### AUDIT-001 — Heartbeat interval not unref'd prevents process exit

- Severity: P1
- Confidence: high
- Area: tools/toolAdapter.ts
- Evidence: `src/tools/toolAdapter.ts:422`
- Reproduction: Read the `withTrackedOperation` function. The `setInterval` at line 422 creates a 1-second heartbeat timer that is `clearInterval`'d in the `finally` block (line 434) but never calls `.unref()`. Compare with `src/driver/BrowserBridgeClientHeartbeat.ts` which correctly calls `this.timer.unref?.()`.
- Expected: Heartbeat timer should be `.unref()`'d so it doesn't keep the Node.js event loop alive.
- Actual: Non-ref'd interval keeps the process alive after all other work completes. When a tracked operation hangs or the main event loop has no other work, the process will not exit.
- Impact: Every tool invocation that enters `withTrackedOperation` (execute, command, evidence, wait, network, hook, frame, web security) creates one of these. In daemon mode this prevents restart; in test mode tests hang.
- Suggested fix direction: Add `heartbeat.unref?.()` immediately after the `setInterval` call at line 422.
- Verification command: `grep -n 'unref' src/driver/BrowserBridgeClientHeartbeat.ts src/tools/toolAdapter.ts`
- Notes: Pattern violation — the sibling class does this correctly.

### AUDIT-002 — Raw params.tabId passed to executeJavaScript while normalized tabId used for monitoring

- Severity: P1
- Confidence: high
- Area: tools/registerExecuteTool.ts
- Evidence: `src/tools/registerExecuteTool.ts:154,170`
- Reproduction: Read the non-monitor branch of `browser_execute` registration (lines 169-171). `normalizeTabId(params.tabId)` is called at line 154 producing a `number`, but `server.executeJavaScript` at line 170 receives the raw `params.tabId` (could be `string`, `undefined`, or `number`).
- Expected: Both the monitoring wrapper (`withExecutionEffect`) and the actual execution should use the same normalized `tabId`.
- Actual: `withExecutionEffect` receives the normalized `tabId` (line 169), but the inner `server.executeJavaScript` call receives `params.tabId` (line 170). If `normalizeTabId` resolves an undefined/implicit tabId to the active tab, the execution effect monitors one tab while the actual execution may target a different resolution.
- Impact: Silent monitoring corruption — execution effects (navigation detection, mutation counting) may be attributed to the wrong tab, producing misleading feedback for agents.
- Suggested fix direction: Replace `params.tabId` with `tabId` on line 170.
- Verification command: `grep -n 'tabId: params.tabId' src/tools/registerExecuteTool.ts`

### AUDIT-003 — Unbounded operations Map in BrowserOperationRegistry

- Severity: P2
- Confidence: high
- Area: driver/BrowserOperationRegistry.ts
- Evidence: `src/driver/BrowserOperationRegistry.ts:10,12-33`
- Reproduction: Read the `BrowserOperationRegistry` class. The `operations` Map (line 10) has no TTL sweep and no size limit. Operations are only removed when `finish()` is called (line 56-61). Compare with `BrowserObservationSnapshotRegistry` which has `pruneExpiredByTtl()`.
- Expected: Stale operations should be pruned after a timeout to prevent unbounded memory growth.
- Actual: If the process crashes or an operation handle's `finish()` is never called, the record persists in memory indefinitely.
- Impact: Gradual memory growth in long-running daemon processes. Over the lifetime of a daemon serving many tool invocations, stale operation records accumulate.
- Suggested fix direction: Add a TTL sweep (e.g., prune operations older than 5 minutes on each `snapshot()` call) or add a max-size eviction policy.
- Verification command: `grep -rn 'pruneExpired\|TTL\|ttl' src/driver/BrowserObservationSnapshotRegistry.ts`

### AUDIT-004 — WebSocket connections not forcefully closed on server stop

- Severity: P2
- Confidence: high
- Area: driver/BrowserBridgeHttpServer.ts
- Evidence: `src/driver/BrowserBridgeHttpServer.ts:119-133`
- Reproduction: Read the `stop()` method. `this.wss?.close()` (line 123) stops accepting new WebSocket connections but does NOT terminate existing client connections. The `ws` library's `Server.close()` only stops accepting — it does not call `.close()` on each connected socket.
- Expected: `stop()` should iterate all connected WebSocket clients and close them before closing the server.
- Actual: Existing WebSocket sockets remain open until clients disconnect or idle timeouts fire. During `BrowserBridgeServer.stop()`, the caller clears registries and pending requests but the underlying sockets are still connected.
- Impact: Delayed process exit after stop(); potential resource leak of socket handles; pending callbacks on closed sockets may fire errors after the server is "stopped."
- Suggested fix direction: Before `this.wss?.close()`, iterate `this.wss.clients` and call `.close()` on each.
- Verification command: `grep -n 'clients' src/driver/BrowserBridgeHttpServer.ts`

### AUDIT-005 — leaseOwnerHash returns raw session UUID instead of hash

- Severity: P2
- Confidence: high
- Area: driver/BrowserBridgeServer.ts
- Evidence: `src/driver/BrowserBridgeServer.ts:294-298`
- Reproduction: Read the `leaseOwnerHash` method. It returns `lease?.browserSessionId` (the raw UUID string) at line 297. The companion `BrowserOperationRegistry.ownerHash()` (lines 4-7 of `BrowserOperationRegistry.ts`) correctly hashes with SHA-1. But `leaseOwnerHash()` returns the raw UUID, not a hash.
- Expected: The method should hash the browserSessionId before returning, matching the privacy pattern in `ownerHash()`.
- Actual: Raw session UUIDs are exposed in operation tracking snapshots (via `BrowserActiveOperationInfo.leaseOwnerHash`), defeating the hashing privacy measure. The value is passed through `registerExecuteTool.ts:164` into tracked operations.
- Impact: Privacy/compliance concern — raw session UUIDs visible in operation tracking and diagnostics where only a truncated hash should be visible.
- Suggested fix direction: Apply `ownerHash(lease?.browserSessionId)` instead of returning `lease?.browserSessionId` directly.
- Verification command: `grep -n 'leaseOwnerHash' src/driver/BrowserBridgeServer.ts src/tools/registerExecuteTool.ts`

### AUDIT-006 — verifyMemoryAnchors reports "fresh" when live anchor is absent

- Severity: P2
- Confidence: high
- Area: memory-core/staleness.ts
- Evidence: `src/memory-core/staleness.ts:11-18`
- Reproduction: Read the `verifyMemoryAnchors` function. Every staleness check requires BOTH `anchors.X` and `live.X` to be truthy (lines 14-16). If `anchors.canonicalUrl` is `"https://example.com/page"` but `live.canonicalUrl` is `undefined` (page navigated to `about:blank`, or live capture failed), the check is skipped.
- Expected: When `anchors.X` is truthy and `live.X` is falsy, that should be treated as stale (the anchor can no longer be verified).
- Actual: The function returns `{ status: "fresh" }` because no stale comparison was triggered. A memory recorded on `https://example.com/dashboard` is considered "fresh" after navigating to `about:blank`.
- Impact: False-fresh state causes stale memory to be recalled and acted upon with outdated context. This undermines the entire memory staleness verification system.
- Suggested fix direction: Add checks like: `if (anchors.canonicalUrl && !live.canonicalUrl) stale.push("canonicalUrl")` (and similarly for stampSetId and fingerprintSummary).
- Verification command: `grep -n 'live\.' src/memory-core/staleness.ts`

### AUDIT-007 — causalUserTriggeredCount silently undercounts on capped requests array

- Severity: P2
- Confidence: high
- Area: abml-core/causal.ts
- Evidence: `src/abml-core/causal.ts:54-57`
- Reproduction: Read `causalUserTriggeredCount` (lines 54-57) and compare with `causalRequestsFiredCount` (lines 49-52). The requests array is capped at `MAX_CAUSAL_REQUESTS = 12`. `causalRequestsFiredCount` correctly uses `causal.requestCount` for the true total, but `causalUserTriggeredCount` uses `causal.requests.filter(...).length` which only counts within the capped array.
- Expected: The function should account for the capped array, similar to `causalRequestsFiredCount`.
- Actual: On a real SPA navigation with 40 requests (30 user-triggered), `causalUserTriggeredCount` returns at most 12 instead of 30.
- Impact: Agent misjudges action effect magnitude, leading to incorrect causal attribution and missed follow-up actions. The sibling function already has the fix pattern.
- Suggested fix direction: Add a `userTriggeredCount` field to `CausalSummary` (mirroring `requestCount`) or compute a ratio-based estimate when the array is truncated.
- Verification command: `grep -n 'requestCount\|MAX_CAUSAL' src/abml-core/causal.ts`

### AUDIT-008 — safeRegex misses ReDoS-vulnerable nested alternation patterns

- Severity: P2
- Confidence: medium
- Area: utils/safeRegex.ts
- Evidence: `src/utils/safeRegex.ts:4-13`
- Reproduction: Read the `unsafeRegexReason` function. The `nested_quantifier` check (line 10) uses `\([^)]*` which stops at the first `)`, so it cannot match patterns with nested parens like `((?:a|b)+)+`. The `quantified_alternation` check (line 11) similarly fails on nested groups. Patterns like `(?:a|b+)+` or `(?:a|aa)+` pass all checks but cause exponential backtracking.
- Expected: The safety check should catch all common ReDoS-vulnerable patterns.
- Actual: Several dangerous patterns pass the safety gate:
  1. `(?:a|b+)+` — inner group quantifier not detected
  2. `(?:a|aa)+` — overlapping alternation not detected
  3. `((?:a|b)+)+` — nested group with quantifier not detected
- Impact: User-supplied regex patterns (from scan templates, matcher configs, or fuzz mutations) could contain ReDoS-vulnerable patterns that pass the safety check and cause CPU exhaustion when matched against attacker-controlled input.
- Suggested fix direction: Add a check for nested quantified groups using a more sophisticated pattern or a simple parser that tracks parenthesis depth. Consider using the `re2` library or a dedicated ReDoS checker.
- Verification command: `echo '(?:a|aa)+' | node -e "const {unsafeRegexReason}=require('./dist/utils/safeRegex.js');console.log(unsafeRegexReason(require('fs').readFileSync(0,'utf8').trim()))"`

### AUDIT-009 — Diff churn salience score hardcoded to 0

- Severity: P2
- Confidence: medium
- Area: abml-core/diff.ts
- Evidence: `src/abml-core/diff.ts:162-171`
- Reproduction: Read the diff salience summary builder. The churn item's `score` is hardcoded to `0` at line 165. The `items` array (line 178) sorts by score descending, so churn items always sort to the bottom.
- Expected: Churn score should reflect the magnitude of entity appearance/disappearance (e.g., `Math.min(100, (appeared + disappeared) * 2)`).
- Actual: A massive page transition (50 appeared + 50 disappeared) gets score 0, same as a minor one (1 + 1). The agent cannot distinguish major transitions from minor ones in the salience ranking.
- Impact: Diff salience summary is how the agent decides which changes to investigate. A page that just loaded a completely new view has churn score 0 while a single text update on an entity gets score 28-68, leading the agent to focus on minor changes while missing major transitions.
- Suggested fix direction: Compute score as `Math.min(100, (diff.appeared.length + diff.disappeared.length) * 2)` or similar magnitude-based formula.
- Verification command: `grep -n 'score: 0' src/abml-core/diff.ts`

### AUDIT-010 — TOCTOU race in readOrCreateMemorySecret

- Severity: P2
- Confidence: medium
- Area: memory/secret.ts
- Evidence: `src/memory/secret.ts:29-36`
- Reproduction: Read `readOrCreateMemorySecret`. Step 1: `readMemorySecret(cwd)` returns `undefined`. Step 2: `randomBytes(SECRET_BYTES)` generates a new secret. Step 3: `atomicWriteText` writes it. If two concurrent callers both reach step 1 simultaneously, both see no existing secret, both generate different secrets, both write (via `atomicWriteText` which uses `rename`). One write wins, the loser returns a secret that doesn't match on-disk.
- Expected: The function should be safe under concurrent access, or document that it is not.
- Actual: The losing caller returns a secret that differs from what's on disk. HMAC stamps created with the losing secret won't verify against future calls that read the winning secret.
- Impact: Parallel memory operations can produce unverifiable stamps, causing false "stale" verdicts on memory anchors. The window is narrow (one disk write) but real under concurrent load.
- Suggested fix direction: After writing, re-read the file to confirm the on-disk secret matches, or use a file lock (e.g., `proper-lockfile`).
- Verification command: `grep -rn 'readOrCreateMemorySecret' src/`
